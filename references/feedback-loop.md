# 持续训练反馈与计划修订

本Skill是持续循环：初始规划 → 当天执行 → 反馈 → 确认原因与恢复 → 修订剩余周/后续阶段。一次表现差不自动下调FTP，一次表现好也不立即加量。

## 接到“练完了 / 爆了 / 没完成 / 感觉太轻松”后

先提取已知内容，再集中补问，别重复用户刚说过的数据：

> 全课RPE是几分（0–10）？主间歇最后一组几分？完成了哪些段、第几分钟开始掉功率？更像饿/能量突然没了、腿部局部无力/酸胀，还是呼吸和心率先撑不住？也可能混合或说不清。骑前吃了什么、骑中多少克碳水/小时、何时吃；补水、天气/散热、睡眠、近期练腿和疲劳如何？现在有没有疼痛、头晕或其他不适？

不要让用户在“燃料/腿力/有氧”之间必须单选，更不能由RPE或心率单独诊断病因。有实际活动数据时请求可用的功率、心率、时长和真实TSS；否则保留主观反馈，不编造实际指标。严重胸痛、晕厥、意识异常等先停止训练并就医，不继续排强度。

## 原因线索 → 小步调整

- **疑似供能不足**：出现时间、总时长、进食与碳水摄入不足等共同支持时，先补给与恢复，调整下一次长骑的补给时机/携带和既往耐受范围。后续24–48h先取消或推迟质量课，恢复后评估；不立即认定有氧能力差或砍FTP。
- **局部腿部限制**：近期重腿、低踏频高扭矩、站姿冲坡、局部酸痛等线索；减少接下来腿部高负荷，换更轻齿比/缓坡、缩短有效间歇或减少重复，保留轻松骑或休息。不是一句“腿无力”就诊断肌力不足。
- **呼吸/心血管负担先到顶**：结合热环境、节奏过快、FTP/分区设置、热身与恢复；优先降低峰值、缩短工作段、延长恢复或换轻松骑。反复在良好补给/恢复下仍无法完成才考虑重新评估区间；不能凭一次失败确诊“有氧不够”。
- **热/脱水、睡眠/全身疲劳或混合**：先降温、恢复和降低计划压力，停止叠加热适应/高强度。信息不足时用保守临时方案，并说明待确认的问题。
- **明显比预期轻松且恢复好**：记录完成质量与次日反馈，多次同类课稳定完成后才小幅增加一个维度，不同时增加强度、时长与组数。

缩短10–20%或减1组可作为清楚标注的下一次试探，不是自动治疗剂量。明确调整是由哪些线索支持、置信度/未知是什么，以及下次如何验证。RPE是0–10分；`session-RPE × minutes`可另记作任意单位，**不能冒充TSS**。

## 每次给用户看的修订结果

1. 已完成事实：计划/实际时长、完成率、全课与主组RPE、实际/估算TSS及来源。
2. 暂定解释：支持证据、其他可能性、尚待回答的问题。
3. 接下来24–48h：休息/轻松/质量课的具体替换与恢复复查条件。
4. 剩余周：列出改变的日期和课表、原周TSS目标、已完成TSS、修订后预计总TSS、低中高时间分布/PI变化（可算时）。未完成的TSS不当作欠债。
5. 下个检查点：例如次晨腿感、睡眠与RPE，或下一次相同目标课；稳定后再决定是否回原计划。

没有后续数据就不能说“已经恢复”。局部调整不默认覆盖整周期；改变主目标、比赛日期或长期时间预算时才重新倒排。

## 延续记录 / 不假装拥有永久记忆

有文件读写能力时，使用 `save_athlete_profile`、`save_training_plan`、`record_training_feedback` 或 `scripts/training_plan.py` 维护 Git 忽略的 `.training-state/`。档案保存 FTP 来源/日期、阈值、时间约束、语言和单位偏好；计划保存版本、原因与差异；真实反馈追加保存并关联当时的计划版本。后来的处方变化不会改写历史实际数据或原比较结果。已有 `state.json` 保留，按真实字段逐步迁移。

新会话先读最新档案、计划和反馈，确认目标/FTP/可用时间是否变化后再调整。没有持久存储能力时提供可复制续接摘要，不声称跨聊天自动记得。

日历修改用稳定的 `plan_id` / `session_id`，先 `preview_training_plan`，按已有用户授权 `sync_training_plan` 并回读验证。移除课表不会自动删除平台事件；遗留事件会被列出。超时或部分成功先回读，不重复创建替代修改。格式、状态和命令以 [Implementation Details](../docs/IMPLEMENTATION.md) 为准。
