# 功率画像：可运行的追问、只读回溯与候选估计

适用于只给CP20/P20、希望补齐短时成绩、读取Intervals.icu历史，或比较FTP候选的请求。`CP20`等旧称在此仅指20分钟最佳平均功率；`CP`模型参数另行命名。

## 1. 各模型统一采用的交互

用户只说“20分钟250W”时，先调用`prepare_power_profile(cp20_watts=250)`，或按同样规则询问：

> 是否知道自己的6s、30s、1m、3m、5m、12m、40m和60m最佳平均功率？知道的提供即可，不知道可以留空；也可以授权读取Intervals.icu。已给的20分钟成绩不再重复询问。请补充成绩日期、设备、室内外、是否接近全力及测试协议；体重用于功体比画像。

只问影响当前计划的缺失项，按答案逐步深入，不把九个功率点变成必填问卷。明确的近期FTP可先保留；用户答不出详细问题或希望先开始时，按第3节说明假设并用理论兜底给首版，不停在“数据不全”。授权读取过的数据优先利用，避免重复手填。用户不懂FTP、TSS或PI时，先用一句话解释，再问日常训练感受或给出推荐。

## 2. 默认回溯实际做什么

- `get_power_curve_evidence(newest_date="YYYY-MM-DD")`：只读`42d、90d、365d`三个窗口，主分析90d；日期按运动员当地日期传入，不能按服务器时区猜。
- 从`secs/watts/activity_id`逐项提取6/30/60/180/300/720/1200/2400/3600秒，并关联源活动日期和当时体重。API只给汇总曲线，未读原始流时，设备/最大努力/采样质量保留未知。
- 返回API实际起止和`days`。平台`90d`可能返回91个日历日期，不把标签伪装成精确90天；365d只作历史背景。
- 返回各平台功率模型的eFTP/CP/W′，以及本地3/5/12分钟模型比较、敏感性和长时交叉检查。它们都是候选证据，不自动更改FTP。
- 缺6s不拿5s或瞬时峰值顶替；未知努力不能当短板；不同窗口同一次纪录不能算多次独立验证。低功率、旧纪录、局部倒挂都先展示出处并核查。
- 一并读取所需最少活动元数据，区分“贡献最佳值的活动数”和“窗口内可确认的训练记录数”。类型/日期/功率字段缺失保留为未知；最多1000条并标记可能截断，不能把平台限制形成的空白认定为没训练。
- `get_steady_ride_evidence(activity_id, start_seconds=900, duration_seconds=2400)`：只读时间/功率/心率/踏频，描述指定连续稳态窗口。缺测、非连续1Hz或无心率就返回原因，不插值造数，不读取GPS。

## 3. 按水平估计：可以采用什么数值

[Sitko等2023年原始研究](https://pubmed.ncbi.nlm.nih.gov/37802084/)纳入120名骑士，以VO2max区分组别，用20分钟功率预测60分钟功率。可用的分组系数是：

- recreational：0.88。
- trained：0.92。
- well_trained：0.95。
- professional：0.96。

验证集平均绝对误差由27W改善至25W，R²由0.51改善至0.54。**这是群体P60预测，不是乳酸阈值公式；25W不是个人±25W置信区间。**分组以VO2max为依据，不能声称论文按FTP W/kg给出了这些系数。

规划中分别处理两件事：

1. **训练剂量**：由目标、近期实际训练、时间、偏好与恢复共同决定。功体比可展示趋势或辅助理解专项需求，不再用固定W/kg边界强制分档、固定百分比减量或完整复刻Pro课表。工具输出中若仍有`scaling/tier`，视为旧计算器提示，不是Agent排课规则。
2. **P60暂用参考**：优先问简单的训练经历和成绩来源。用户不能回答细节时，可说明假设后暂选上述分组系数给出起步方案，之后通过完成质量、RPE和恢复更新。完全无法区分组别时，可先用0.88作较低的工作假设；这是Skill的缺省选择，不是研究证明未知用户都属于休闲组，也不保证对每人恰好合适。

有VO2max检测或用户明确自述时记录真实依据。无组别证据时写“模型暂按某组假设”，不能把假设伪填成检测/自述，也不用固定功体比边界替代原研究分组。明确P20为非全力训练时依照第4节保留RPE方案，不把算术结果宣称当前FTP。

例如P20测试=250W，其他信息答不出：可以暂按0.88得到220W，并解释这是群体P60预测的训练参考；其余组候选230/237.5/240W可按需要补充，不必把四个数全丢给用户让其自行选。先从近期可完成的训练安排起步，给出“太累就缩短/降强度、连续完成且恢复好再增加”的条件，逐渐替换群体估计。

可直接使用的说明：

> 你现在只知道20分钟测试250W，其他数据暂时没有也可以开始。我先按休闲训练组0.88作假设，得到约220W的暂用训练参考。这不是你的实测FTP或LT2；研究按VO2max分组，而我们暂时没有这项检测，实际值可能不同。先按你最近能完成的时长安排，结合骑行时0–10分的费力程度和次日恢复来调整，之后有条件再补测。

原引擎根据P1/FTP比例选择0.92或0.96的分支已移除；P1不能用于诊断VLamax或决定研究组。当前CLI仍会返回追问/候选，兼容生成MCP仍要求最大努力声明、组别/依据和采纳参数；**这些工具校验不要求Agent把对话卡在问卷上**。Agent可按本节计算并展示注明假设的暂定方案/RPE课表，不能声称工具已自动选组、伪填最大努力或已经修改账号。写日历仍遵循实际授权与现有预览流程。

## 4. CP、LT1、LT2与输出边界

- 两种两参数CP拟合使用3/5/12分钟，报告功率–逆时间与做功–时间的差异，以及删除锚点后的敏感性。6s/30s/1m不塞进此模型。
- 历史最大平均曲线的努力状态默认未知；来源少或日期跨度大要提示。局部拟合好不证明FTP/LT2准确，长时比较也可能包含疲劳、配速与补给差异。
- 如果用户明确说这些只是日常训练，传入`effort_status="training_not_maximal"`：停止将这些点拟合为能力候选，分组乘数只作假设展示，不据此推断当前FTP。旧FTP保留原来源与失效疑问；不能把“旧FTP过期”解读成“必须降低到近期训练最佳值”。
- 稳态窗口报告平均功率/心率、功率变异系数、心率–功率解耦；即使解耦较小也不把它当LT1。继续问RPE、谈话、温湿度、补给与恢复。
- 乳酸LT1/LT2未测就保持未知。已有报告按原协议独立录入；VT1/VT2、MLSS、CP与FTP分别命名。
- 只读工具不会把候选自动写成正式阈值或改动日历。Agent可在说明假设后以暂用参考完成首版规划；持久化时保留“群体估计/模型假设”的来源，不能标成实测。后续采纳经验证设置时，按版本机制复算未来TSS/PI并展示差异。完整后续路线见[评估方案](power-curve-assessment-plan.md)。

## 5. 可复制运行方式

先安装仓库requirements，使用对应Python环境。离线追问不需账号：

```powershell
python -X utf8 scripts/power_profile.py --cp20 250 --weight 70
```

真实账号试跑通过**实际MCP stdio握手和工具调用**完成，而不是把HTTP请求冒称MCP。凭据沿用环境变量；可显式读取本地被Git忽略的`.env`中的两个Intervals键，密钥不输出：

```powershell
python -X utf8 scripts/power_profile.py --live --env-file .env --as-of 2026-10-20 --steady --out .training-state/power-assessment-2026-10-20/report.json
```

日期需替换为用户当地实际评估日；`--steady`最多读取主窗口中两个长时节点源活动的热身后40分钟。这是便于试跑的候选窗口，不保证活动为稳态，必须结合功率变异和用户反馈判断。实际调用名记录在报告中，远程调用均为GET。报告保存于`.training-state`，不把真实成绩或源活动ID加到README/公开fixture。

CLI输出JSON；重点看`curves[].points`、`quality_flags`、`intake.followup_questions`、`group_candidates`、`cp`、`thresholds`、`steady_windows`和`account_writes`。如API受权限/数据来源限制，保留缺失原因，转为用户导出/手填，不假设缺数据等于没有训练。

可用`--context-file`传入私有JSON，例如`{"effort_status":"training_not_maximal","working_ftp_note":"来自旧测试，当前尚未复测"}`；相同字段也可直接传给`get_power_curve_evidence`。反馈改变的是证据解释，不会修改账号设置。
